## 1. 需求背景与目标

现有 MVP 已跑通「输入 → 出题 → 答题 → 报告」核心闭环，但**无登录、无持久化**：用户身份不存在、金币不落地、答题记录与报告一次性丢失。

本次追加**用户系统**，目标：

1. 用户拥有持久身份（微信静默登录，无感进入）；
2. 答题金币落地（跨设备累计），为留存与后续排行榜打基础；
3. 答题记录与 AI 复盘报告持久化，支持日后复盘；
4. 个人中心落地「后台分析」（对应需求文档 P1「后台错题与分析复盘」中的分析部分），即扩展原型屏 1「我的林间日志」。

## 4. 功能需求明细

### 4.1 用户登录与鉴权

- [ ] 前端启动时静默登录：`Taro.login()` 获取 code → 调登录接口 → 存储 token 与用户信息
- [ ] 后端登录接口：接收 code →（MOCK 模式）生成固定 mock 用户 /（正式模式）调微信 `code2session` 获取 openid
- [ ] 老用户按 openid 识别（幂等登录），新用户自动注册（默认昵称「林中客」、头像「林」、金币 0）
- [ ] 登录成功返回 JWT token（有效期 7 天）与用户信息（昵称、文字头像、金币余额）
- [ ] 用户相关接口全部要求 JWT 鉴权，未带/失效 token 返回 401
- [ ] 前端请求统一携带 token；收到 401 自动重新静默登录并重试一次，仍失败提示用户

### 4.2 用户信息

- [ ] 查询当前用户信息（含金币余额、学习统计汇总）
- [ ] 编辑昵称（微信昵称填写能力，≤16 字），文字头像自动同步为昵称首字
- [ ] 昵称非法（超长/敏感词）返回明确错误提示

### 4.3 答题金币

- [ ] 闯关完成时一次性提交全部作答，服务端重新判分（不信任前端）
- [ ] 单题结算：答对 +10 / 答错 −5；余额不足扣减时按余额封底（不为负）
- [ ] 逐题生成金币流水（原因：答对/答错），并同步更新用户金币余额，同事务完成
- [ ] 防刷：同一用户同一内容 24h 内已计入金币的闯关，本次金币变动为 0（记录仍保存）
- [ ] 结算幂等：同一闯关重复提交不重复入账（客户端生成会话唯一键）
- [ ] 接口返回：本关金币变动、本次是否计入金币、最新余额
- [ ] 闯关页每题作答后展示「+10 金币」/「−5 金币」（本地即时反馈，与结算结果最终一致）

### 4.4 闯关记录与历史报告

- [ ] 每次闯关落库：内容、主题、题目快照、作答记录、判分结果（题数/答对数/正确率）、金币变动
- [ ] AI 复盘报告生成后关联到对应闯关记录（复用现有报告生成能力）
- [ ] 查询最近闯关列表（主题、日期、正确率），供个人中心「最近复盘」展示
- [ ] 按闯关记录查看历史报告（题目、作答、AI 报告全文），不再重新调 AI

### 4.5 个人中心 · 学习分析（扩展原型屏 1）

UI 必须完全按 `prototype/02-extended-flow.html` 屏 1 实现（章节名「我的林间日志」、卡片样式、色彩体系与现有小程序一致）：

- [ ] **用户信息区**：文字头像（昵称首字）+ 昵称 + 副标题「已漫步 X 次 · 累计答对 Y 题 · 金币 Z」+ 编辑资料入口
- [ ] **统计卡（4 张）**：闯关数 / 总正确率 / 掌握知识点数 / 金币余额
- [ ] **近七日答题柱状图**：按日统计答题数（题目数），今日柱高亮为晨光金色，其余湖水青碧渐变；图例「答题数 / 今日」
- [ ] **我的知识树**：知识点气泡标签集合（近期学过，高频知识点为核心样式深色气泡），配树枝 SVG 装饰
- [ ] **最近复盘**：最近 5 条闯关记录（主题 + 相对时间 + 正确率），点击进入历史报告页
- [ ] **空态**：无学习记录时展示现有空态卡片（「暂无学习记录」文案与占位页一致），并提供「去漫步」引导按钮

### 4.6 前端整体要求

- [ ] 登录态管理：token 持久化，跨会话保持登录
- [ ] 未登录（登录失败）时：核心闯关流程仍可使用，但金币与记录不入账，页面有登录失败提示
- [ ] 报告页支持两种模式：新报告（生成后展示）与历史报告（从服务器读取），UI 一致
- [ ] 交互风格、色彩、衬线字体等与现有「湖畔手账」设计系统严格一致

## 5. 需求批次与优先级

按「依赖关系 + 业务价值」划分，每批次可独立验收，完成一批验收一批：

| 批次 | 名称 | 优先级 | 内容 | 验收标准 |
| --- | --- | --- | --- | --- |
| **P0** | 基础设施 | 最高 | MySQL Docker Compose 环境（`ai-learn-mysql`，端口顺延）；SQLAlchemy 异步接入；三张表建表（users / quiz_sessions / coin_transactions）；配置项与启动脚本 | `docker compose up` 成功；启动脚本一键起库；应用连库成功，建表完成；`GET /health` 200 |
| **P1** | 用户登录与鉴权 | 最高 | 登录接口（MOCK 开关）、JWT 签发/校验、前端静默登录、请求带 token、401 自动重登录 | 登录返回 token + 用户信息；无 token 访问受保护接口 401；重启应用后登录态仍有效 |
| **P2** | 用户信息与个人中心 | 高 | 用户信息查询/编辑接口；个人中心屏 1 完整 UI（统计卡/柱状图/知识树/最近复盘/编辑资料）；空态展示 | 屏 1 UI 与原型一致；编辑昵称生效且头像首字同步；无数据时空态正确 |
| **P3** | 闯关结算与金币 | 高 | 闯关结算接口（判分/流水/余额/幂等/防刷）；闯关页逐题金币提示；金币余额展示 | 单题 +10/−5 正确；余额不为负；同内容 24h 二次闯关金币为 0；重复提交不重复入账；闯关页金币提示即时展示 |
| **P4** | 记录持久化与历史报告 | 中 | 报告关联闯关记录；历史报告查看接口；「最近复盘」列表有真实数据；报告页历史模式 | 闯关记录完整落库；历史报告可完整查看（与生成时一致）；最近复盘列表数据正确 |
| **P5** | 整体联调与回归 | 中 | 真机/开发者工具完整闭环回归；MVP 核心功能回归（出题/答题/报告/海报） | 登录 → 出题 → 答题（金币反馈）→ 报告 → 个人中心统计与历史一致；MVP 旧功能无回归 |

**批次依赖关系**：P0 → P1 → P2 → P3 → P4（P5 最后整体验收）。P2 的统计/历史数据在 P3/P4 落地后自然填充，P2 阶段以空态验收。

## 6. 测试要求

- 后端全部新功能必须 TDD 覆盖（pytest）：
  - 登录与鉴权：MOCK 登录、JWT 签发/校验、401 场景、token 过期
  - 金币结算：判分正确、+10/−5、余额封底、防刷、幂等
  - 记录与报告：落库完整性、历史查询、报告关联
  - 个人中心聚合：统计卡/七日柱状图/知识树/最近复盘计算正确
- 前端以手测清单为主（开发者工具 + 真机），覆盖登录、闯关金币反馈、个人中心、历史报告查看、编辑昵称、MVP 回归
